# `infra/lambda/src/recipes/getRecipes.ts` レビューコメント和訳と妥当性評価

## 1. JWT の `userId` 取り出し時の型検証

### 和訳
JWT クレームから `userId` を取り出す際に、値が実際に文字列か確認せず、型アサーション（`as string`）を使っています。
続く行の falsy チェックで空値は弾けますが、`sub` クレームが文字列以外の不正な JWT の場合に検証をすり抜ける可能性があります。
型安全性を確保するため、`if (!userId || typeof userId !== 'string')` のような明示的な型検証を追加することを検討してください。

### 妥当性
**概ね妥当です。** TypeScript の `as string` は実行時検証にならないため、`sub` が `number` や `object` でもコンパイル上は通ります。
ただし API Gateway の JWT Authorizer が事前検証するため、実運用での発生確率は低いです。
それでも Lambda 境界で `typeof` を入れて防御を厚くする提案は有益です。

## 2. 例外処理が常に 500 になる点

### 和訳
汎用的なエラーハンドリングで全ての例外を捕捉し、汎用メッセージ付きの 500 を返しています。
情報漏えい防止には有効ですが、デバッグが難しくなります。
`ResourceNotFoundException`、`AccessDeniedException` など DynamoDB のエラー種別を判定し、適切な範囲でより具体的なエラーメッセージを返すことを検討してください（本番では機微情報を出しすぎない前提）。

### 妥当性
**妥当です。** 現状は観測性の面で改善余地があります。
一方で、`docs/04-api-design.md` は 500 の基本形を許容しつつ `code` を増やす方針なので、段階的な詳細化が設計方針にも合います。
「本番レスポンスは汎用、詳細はログへ」の切り分けが現実的です。

## 3. `userId` を先頭 8 文字でログ出力している点

### 和訳
`userId` を 8 文字に切って記録するプライバシー配慮は良い実践です。
ただし、デバッグしやすさとプライバシー保護のバランスとして、この長さが十分か確認してください。
（Cognito の UUID 形式次第では）複数ユーザーの先頭 8 文字が一致し、デバッグ時に識別が曖昧になる可能性があります。

### 妥当性
**妥当です。** 指摘はリスク説明として正しいです。
特にユーザー数増加時は衝突可能性が上がるため、8 文字固定より、
- 12 文字程度へ拡張
- あるいはハッシュ短縮値（例: SHA-256 の先頭）
などが候補になります。

---

## 4. `Recipe` 型（DynamoDB エンティティ）と API レスポンス型の分離

### 和訳
`shared/types.ts` の `Recipe` 型では `userId` が必須ですが、レスポンスへのマッピングでは `userId` を返していません。
`docs/04-api-design.md` 上は `userId` 非公開が正しい一方で、行 47 の型キャストで `userId` にアクセス可能な状態です。
DynamoDB エンティティ型と API 返却形を明確に分けるため、`RecipeResponse` のような別型を作ることを検討してください。

### 妥当性
**非常に妥当です。** 現在の実装は実データの変換自体は正しいものの、
型の責務が混在していて将来の漏えい（うっかり `userId` を返す）を静的に防ぎづらい構成です。
`RecipeEntity`（DB）と `RecipeResponse`（API）を分離すると、仕様準拠と保守性が上がります。

---

## 総評
4 件とも有効な改善提案です。優先度を付けるなら次の順が現実的です。

1. **高**: `userId` の実行時型検証追加（防御的プログラミング）
2. **高**: Entity 型と Response 型の分離（設計の明確化）
3. **中**: 例外の分類と `error.code` の拡充（運用性向上）
4. **中**: ログ匿名化方針の見直し（衝突率と可観測性のバランス調整）
